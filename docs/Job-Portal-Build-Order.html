Job Portal Build Order

Every step checked against your working project rather than written from memory. Start at laravel new, finish with a demo that answers both the PSRS and UTUMISHI papers.

First: what the guide you pasted gets wrong

Four of these would cost you real time in the exam. One is a claim I have to walk back about my own earlier advice, because I checked the framework source and I was wrong.

  • Breaks login

    Seeded users can never get past /verify-email

    The guide seeds with User::create([...]) and never sets email_verified_at. Your User implements MustVerifyEmail, and every route sits behind ['auth', 'verified']. So all three seeded accounts log in and are immediately bounced to a verification screen — with no mail driver configured to escape it.

    Fix: use User::factory()->create([...]). The factory sets email_verified_at => now() for you.

  • Factually wrong

    QUEUE_CONNECTION=sync does not stop the jobs table

    The guide says setting this "prevents Laravel from creating the default jobs table". It does not. That table is created by a migration — 0001_01_01_000002_create_jobs_table.php — which ships with the starter kit and runs regardless of your queue driver. Follow this advice and you hit the name collision anyway, but now you also can't queue anything.

    Fix: leave QUEUE_CONNECTION alone. Name your table job_listings instead (step 4 below).

  • Incomplete — still collides

    Renaming the migration file changes nothing

    "Rename the Job migration to ..._create_job_listings_table" only renames the file on disk. Inside it still says Schema::create('jobs', ...), so it still tries to create a table called jobs and still explodes. The filename is documentation; the string is what runs.

    Fix: change the string inside too, and add protected $table = 'job_listings'; to the model.

  • Missing column

    No has_disability column

    The applications migration has disability_priority — the computed points — but no column storing whether the candidate has a disability. You can save the score and never the fact. The UTUMISHI paper's entire priority rule has nowhere to live.

    Fix: add $table->boolean('has_disability')->default(false);

  • Wrong paths

    Pages/, .jsx, and Auth/Login.tsx

    This kit uses lowercase resources/js/pages/, TypeScript .tsx, and the login page is at auth/login.tsx. Create resources/js/Pages/jobs/index.jsx and Inertia will not find it — you get a blank page and a console error, which is a miserable thing to debug at minute fifty.

  • Actually fine — my earlier claim was wrong

    bcrypt('password') in a seeder is safe

    I was about to tell you this double-hashes and breaks login, because the User model casts 'password' => 'hashed'. I checked the framework source in your vendor/ first, and it doesn't:

    // HasAttributes::castAttributeAsHashedString()
if (! Hash::isHashed($value)) {
    return Hash::make($value);
}
return $value;

    The cast checks whether the value is already a hash and leaves it alone. So bcrypt() there is redundant, not broken. Drop it for clarity, but it wasn't going to cost you anything. Verify before you trust — including when the claim comes from me.

  • Version

    It says Laravel 11. You're on Laravel 13.26.1

    Mostly harmless — the Kernel.php advice is right for any version since 11 — but it means the guide wasn't written against your project. I had this wrong too, and said "Laravel 12" throughout our earlier conversation. Your composer.lock is the authority.

The build, in order

Each step needs the one before it. Don't skip ahead — most "why is this broken" moments in a timed exam are really "I built things out of order".

1

Starter kit

Gives you Fortify auth, Inertia, React, Tailwind, shadcn/ui, Wayfinder and Vite already wired together.

laravel new my-app     # choose React
cd my-app
npm install
npm run dev            # leave this running - it regenerates Wayfinder routes
php artisan serve
Already done for you

Registration, login, password reset, email verification, session management, and 'password' => 'hashed' on the User model. That is PSRS Part 1.a, 1.b and 1.d with zero lines written. Point at the cast during the demo.

2

Role column

PSRS 1.c. Everything else about RBAC hangs off this one column.

php artisan make:migration add_role_to_users_table --table=users
// up()
$table->string('role')->default('viewer')->after('email');

// down()
$table->dropColumn('role');

Add 'role' to the User model's fillable list, then php artisan migrate.

Watch the syntax

This kit declares fillable with a PHP attribute, not a property — #[Fillable(['name', 'email', 'password', 'role'])] above the class. If you go looking for protected $fillable you won't find it.

Trap

string(), never enum(). Enum columns are unsupported on SQLite and need an extra package to alter on MySQL. A string plus an in:admin,editor,viewer validation rule does the same job and never fights you.

The gate in front of your routes.

4

Job model — and the name collision

PSRS Part 2.I. This is the step that catches everyone.

php artisan make:model Job -m

Rename the generated migration to ..._create_job_listings_table.php and change the string inside it:

database/migrations/…_create_job_listings_table.php 
Schema::create('job_listings', function (Blueprint $table) {
    $table->id();
    $table->string('title');
    $table->string('department');
    $table->string('location');
    $table->decimal('salary', 12, 2);
    $table->boolean('is_active')->default(true);
    $table->timestamps();
});
app/Models/Job.php 
class Job extends Model
{
    // 'jobs' is taken by Laravel's queue migration
    protected $table = 'job_listings';

    protected $fillable = ['title', 'department', 'location', 'salary', 'is_active'];

    protected function casts(): array
    {
        return ['is_active' => 'boolean'];
    }

    public function applications(): HasMany
    {
        return $this->hasMany(Application::class);
    }

    public function scopeActive($query)
    {
        return $query->where('is_active', true);
    }
}
Say this if asked

"Laravel reserves jobs for the database queue driver, so the domain model is Job and the physical table is namespaced." That answer earns marks. Renaming the model to Vacancy works too, but then nothing on screen matches the paper's wording.

5

Application model

PSRS 2.II and 2.IV, plus the UTUMISHI disability rule.

php artisan make:model Application -m
Schema::create('applications', function (Blueprint $table) {
    $table->id();

    // constrained() would guess 'jobs' — name it explicitly
    $table->foreignId('job_id')->constrained('job_listings')->cascadeOnDelete();

    $table->string('candidate_name');
    $table->string('candidate_email');
    $table->text('resume_text');

    $table->boolean('has_disability')->default(false);   // the FACT

    $table->unsignedTinyInteger('resume_score')->nullable();
    $table->unsignedTinyInteger('location_priority')->nullable();
    $table->unsignedTinyInteger('disability_priority')->default(0);
    $table->unsignedTinyInteger('final_score')->nullable();

    $table->timestamps();

    // "apply only once per job"
    $table->unique(['job_id', 'candidate_email']);
});
Two traps in one block

One: constrained() infers the table from the column name — job_id → jobs. Ours isn't called that, so you must pass 'job_listings', or the migration dies with "no such table: jobs".

Two: store has_disability as well as disability_priority. The score is derived; the fact is the data. Keep both.

Then php artisan migrate.

6

Scoring service

Where the marks are. The paper demands "classes or modules for separation of concern" — this file is your evidence.

app/Services/ScoringService.php 
class ScoringService
{
    public function resumeScore(string $resumeText): int
    {
        return random_int(1, 10);   // the paper permits mocking
    }

    public function locationPriority(Job $job): int
    {
        return match (strtoupper(trim($job->location))) {
            'REMOTE' => 3,
            'DAR ES SALAAM' => 2,
            default => 1,
        };
    }

    public function disabilityPriority(bool $hasDisability): int
    {
        return $hasDisability ? 3 : 0;
    }

    /** Returns keys named after the columns, so the controller is one line. */
    public function evaluate(Job $job, string $text, bool $hasDisability = false): array
    {
        $resume = $this->resumeScore($text);
        $location = $this->locationPriority($job);
        $disability = $this->disabilityPriority($hasDisability);

        return [
            'resume_score' => $resume,
            'location_priority' => $location,
            'disability_priority' => $disability,
            'final_score' => $resume + $location + $disability,
        ];
    }
}
Two details people drop

Take a Job, not a string. The paper says in bold that points come from the job's location, not the candidate's. Typing the parameter makes passing the wrong one impossible.

strtoupper(trim(...)). A bare match ($job->location) is case-sensitive, so "remote" silently falls to the default => 1 branch and your Remote jobs score wrong.

7

Controllers

Every method is one or two lines. Anything longer belongs in the service.

php artisan make:controller JobController --resource
php artisan make:controller ApplicationController
// JobController
public function index(Request $request)
{
    return Inertia::render('jobs/index', [
        'jobs' => Job::withCount('applications')->latest()->paginate(10)->withQueryString(),
        'canManage' => $request->user()->canManageJobs(),
    ]);
}

public function store(StoreJobRequest $request)
{
    Job::create($request->validated());

    return to_route('jobs.index')->with('success', 'Job posted.');
}

// ApplicationController
public function __construct(private ScoringService $scoring) {}

public function store(StoreApplicationRequest $request, Job $job)
{
    $data = $request->validated();

    $job->applications()->create([
        ...$data,
        'has_disability' => $request->boolean('has_disability'),
        ...$this->scoring->evaluate($job, $data['resume_text'], $request->boolean('has_disability')),
    ]);

    return back()->with('success', 'Application processed successfully.');
}

public function review()
{
    return Inertia::render('applications/review', [
        'applications' => Application::with('job:id,title,location')
            ->orderByDesc('final_score')->get(),
    ]);
}
Why send canManage

The server decides what a user may do and tells React. Never re-implement the role rules in JavaScript — you'd end up with two sources of truth that drift.

8

Routes

The table of contents of your whole app — and your RBAC answer.

Route::middleware(['auth', 'verified'])->group(function () {
    // anyone signed in
    Route::resource('jobs', JobController::class)->only(['index', 'show']);
    Route::post('jobs/{job}/apply', [ApplicationController::class, 'store'])
        ->name('jobs.apply');

    // admin + editor
    Route::middleware('role:admin,editor')->group(function () {
        Route::resource('jobs', JobController::class)
            ->only(['store', 'update', 'destroy']);
        Route::get('applications/review', [ApplicationController::class, 'review'])
            ->name('applications.review');
        Route::get('reports', [ReportController::class, 'index'])->name('reports.index');
    });

    // admin only — assigning roles
    Route::middleware('role:admin')->group(function () {
        Route::get('users', [UserController::class, 'index'])->name('users.index');
        Route::patch('users/{user}/role', [UserController::class, 'updateRole'])
            ->name('users.role');
    });
});
This is the answer to "show me your RBAC"

Three groups, three levels of access, one resource split across two of them. Splitting is legal while the only() sets don't overlap. Note the last group is role:admin without editor — editors manage jobs, only admins manage people.

9

API key

PSRS 1.e. Four minutes, and easy to demo convincingly.

app/Http/Middleware/ApiKey.php 
if ($request->header('X-API-Key') !== config('services.api_key')) {
    Log::warning('Rejected API request', ['ip' => $request->ip()]);

    return response()->json(['error' => 'Unauthorized'], 401);
}

return $next($request);

routes/api.php does not exist. Create it, then register it in bootstrap/app.php:

->withRouting(
    web: __DIR__.'/../routes/web.php',
    api: __DIR__.'/../routes/api.php',   // adds the /api prefix automatically
    commands: __DIR__.'/../routes/console.php',
    health: '/up',
)
Skip install:api

The usual advice is php artisan install:api, but that also installs Sanctum, which a shared-key API doesn't need. One line in bootstrap/app.php does the same job.

Trap

Read the key with config('services.api_key'), never env('API_KEY'). After config:cache, env() returns null everywhere outside config/ and your API rejects every valid key.

React pages

Three files. The same form block, three times.

FileHolds
pages/jobs/index.tsxTable + one inline form doing create and edit
pages/jobs/show.tsxJob detail + apply form with the disability checkbox
pages/applications/review.tsxRead-only table, the five named columns

Copy the <Form> pattern from resources/js/pages/auth/login.tsx:

<Form {...jobs.store.form()} resetOnSuccess className="grid gap-4">
    {({ processing, errors }) => (
        <>
            <Label htmlFor="title">Title</Label>
            <Input id="title" name="title" required />
            <InputError message={errors.title} />

            <Checkbox name="has_disability" value="1" />

            <Button type="submit" disabled={processing}>
                {processing && <Spinner />}
                Save
            </Button>
        </>
    )}
</Form>
Three traps, all silent

jobs.store.form() — .form is a property of the helper. jobs.store().form() is undefined.

value="1" on the checkbox. Without it a ticked box sends "on", which fails Laravel's boolean rule — so every candidate silently scores zero disability points.

After paginate() the rows are page.data, not page. A blank table right after adding pagination is always this.

Editing in place

<Form> is uncontrolled — it reads the DOM. So use defaultValue, not value, and put a key on the Form so React remounts it when you switch which row you're editing. Without the key, the previous row's text stays on screen and it looks like your backend is broken.

How to add a page — the rules nobody writes down

Inertia has no configuration file listing your pages. It works on naming conventions instead, and when you break one you get a blank screen rather than an error that tells you what's wrong. These are the contracts.

Rule 1 · The name is the path

Inertia::render('jobs/index')  →  resources/js/pages/jobs/index.tsx
Inertia::render('reports/index') →  resources/js/pages/reports/index.tsx

The string is a path relative to resources/js/pages/, with no extension. It is case-sensitive and this kit uses lowercase folders.

How this fails

Write Inertia::render('Jobs/Index') and you get a blank page with "Page not found: ./pages/Jobs/Index.tsx" in the browser console — not a PHP error, not a 500. If a page renders blank, check this first and check the console, always.

Rule 2 · The second argument becomes your props

// controller
return Inertia::render('jobs/index', [
    'jobs' => $jobs,
    'canManage' => $request->user()->canManageJobs(),
]);

// page — the array keys ARE the prop names
export default function Index({ jobs, canManage }: Props) { ... }

Nothing else crosses the boundary. If React can't see a value, the controller didn't send it.

Rule 3 · You never import a layout

resources/js/app.tsx chooses it from the page name:

layout: (name) => {
    switch (true) {
        case name === 'welcome':          return null;
        case name.startsWith('auth/'):    return AuthLayout;
        case name.startsWith('settings/'): return [AppLayout, SettingsLayout];
        default:                          return AppLayout;   // ← your pages
    }
},

So any new page gets the sidebar shell automatically. You only configure it, by assigning an object at the bottom of the file — that object is passed to the layout as props:

Index.layout = {
    breadcrumbs: [{ title: 'Jobs', href: jobs.index() }],
};

That is why auth/login.tsx sets { title, description } instead — AuthLayout takes different props. Same mechanism, different layout.

Rule 4 · Route name decides the import

Route::get('reports', ...)->name('reports.index');
// generates resources/js/routes/reports/index.ts

import reports from '@/routes/reports';   // default export
reports.index()        // { url: '/reports', method: 'get' }
reports.index.url()    // '/reports'
jobs.store.form()      // { action: '/jobs', method: 'post' }  ← for <Form>

Routes are grouped by the first segment of the dotted name, so jobs.index, jobs.store and jobs.apply all land in @/routes/jobs.

If the import doesn't resolve

Wayfinder only regenerates while npm run dev is running. If it isn't, run php artisan wayfinder:generate. Don't assume you typed the name wrong.

Rule 5 · Roles — three layers, only one is security

LayerWhereIs it security?
Route middlewarerole:admin,editorYes. The real gate.
PolicyGate::authorize('delete', $job)Yes. Per-record.
Hidden sidebar linkapp-sidebar.tsxNo. Convenience.
Hidden button{canManage && ...}No. Convenience.

Hiding a link does not stop anyone typing the URL. Always guard the route as well — and in the demo, prove it by typing the URL as a viewer and showing the 403.

Rule 6 · Deciding which group a page goes in

Everyone signed in?     → the outer ['auth', 'verified'] group
Staff only?             → Route::middleware('role:admin,editor')
Admin only?             → Route::middleware('role:admin')

Worked example: a "My Applications" page for applicants

Five files, in this order. Every rule above appears once.

1 · routes/web.php — inside the auth group, no role middleware (any applicant may see their own) 
Route::get('my-applications', [ApplicationController::class, 'mine'])
    ->name('applications.mine');
2 · ApplicationController — scope to the signed-in user 
public function mine(Request $request)
{
    return Inertia::render('applications/mine', [
        'applications' => Application::with('job:id,title,location')
            ->where('candidate_email', $request->user()->email)
            ->latest()
            ->get(),
    ]);
}
The security rule for "my" pages

Middleware can't help you here — every applicant may open this page. What protects the data is the where() clause scoping it to the current user. Drop that line and every applicant sees everyone's applications. Any page called "my something" is protected by its query, not by its route.

3 · resources/js/pages/applications/mine.tsx — matches the render string exactly 
import { Head } from '@inertiajs/react';
import { Badge } from '@/components/ui/badge';
import applications from '@/routes/applications';

type Row = {
    id: number;
    final_score: number;
    created_at: string;
    job: { id: number; title: string; location: string };
};

export default function Mine({ applications: rows }: { applications: Row[] }) {
    return (
        <>
            <Head title="My Applications" />

            <div className="flex h-full flex-1 flex-col gap-4 rounded-xl p-4">
                <h1 className="text-2xl font-semibold">My Applications</h1>

                {rows.length === 0 && (
                    <p className="text-muted-foreground">
                        You haven't applied for anything yet.
                    </p>
                )}

                {rows.map((row) => (
                    <div key={row.id} className="rounded-lg border p-4">
                        <div className="font-medium">{row.job.title}</div>
                        <Badge variant="outline">{row.job.location}</Badge>
                    </div>
                ))}
            </div>

    );
}

Mine.layout = {
    breadcrumbs: [{ title: 'My Applications', href: applications.mine() }],
};
Notice what is missing

No import AppLayout. No <AppLayout> wrapper. Rule 3 handles it — the sidebar, header and breadcrumb bar all appear because the page isn't under auth/ or settings/.

4 · app-sidebar.tsx — the role-gated nav 
const { auth } = usePage().props as unknown as { auth: Auth };

const canManage = auth.user.role === 'admin' || auth.user.role === 'editor';
const isAdmin = auth.user.role === 'admin';

const mainNavItems: NavItem[] = [
    { title: 'Dashboard', href: dashboard(), icon: LayoutGrid },
    { title: 'Jobs', href: jobs.index(), icon: Briefcase },

    // everyone sees this one
    { title: 'My Applications', href: applications.mine(), icon: FileText },

    // staff only
    ...(canManage
        ? [
              { title: 'Review', href: applications.review(), icon: ClipboardList },
              { title: 'Reports', href: reports.index(), icon: ChartColumn },
          ]
        : []),

    // admin only
    ...(isAdmin ? [{ title: 'Users', href: users.index(), icon: Users }] : []),
];

The ...(condition ? [item] : []) spread is the whole trick — it adds the entries or adds nothing, inside one array literal.

Two things that bite here

Build the array inside the component, not at module scope. A const outside the function is evaluated once at import time, before any user exists, so auth.user.role would throw.

Icons come from lucide-react and the name must exist. Import a name that isn't there and Vite fails the whole page, not just the icon.
